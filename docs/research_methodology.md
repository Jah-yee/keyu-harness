# 研究方法

本项目采用**技术考古 + 数字取证思维 + 软件供应链分析 + 可复现实验**的组合方法。它不是某一种单独学科的替代品，而是一套让技术主张可以被追踪、质疑和复核的工作流程。

## 1. 来源批判：先问材料是什么

对每个来源记录发布者、发布时间、来源类型、版本、获取时间、能直接支持的内容和已知局限。报道页面是该页面内容的一手材料，但不自动等于其所展示内部代码、日志或截图的独立保全副本。

## 2. 版本化研究：`main` 不是历史

公开仓库至少记录 canonical URL、tag/commit SHA、parent commit、获取时间、文件树清单和许可信息。事件发生时间、公开发布时间与我们获取材料的时间分别记录，不能混成一条时间线。

## 3. 工件谱系：不要把模型当成一个文件名

分别登记：
- 模型配置与 revision；
- tokenizer 及其文件哈希；
- 权重文件或 shard；
- 文本特征缓存及其生成代码；
- 视觉 tokenizer / codec 工件；
- 主模型 checkpoint；
- 训练配置、环境清单和 job/run 标识。

只有把生产者、输入、产物和消费者连接起来，才可能讨论某个工件是否真的影响了特定任务。

## 4. 可重复的审计：先验证工具

合成案例用来测试解析器是否发现元数据不一致、指标离群或清单缺项。它们不是历史事件的复刻，也不能作为事件证据。报告必须同时给出输入清单、规则、输出和限制。

## 5. 因果克制：异常不是动机，相关不是因果

一条技术因果主张至少需要：
1. 可定位的具体差异；
2. 目标运行确实加载该差异的证据；
3. 与之对应的运行行为变化；
4. 与所述现象相符的时间关系；
5. 可重复的比较或修复实验；
6. 对其他解释的检查。

缺少任何关键环节，都应将结果写成待验证假设或相关性，而不是已证实的因果结论。

## 6. 来源角色与主张状态

来源表不使用单一的数字“可信度分数”。它分别记录：

- `source_role`：材料属于事件材料页、公开源码、论文、模型配置、二手报道、版本基线或方法参考中的哪一类；
- `review_status`：尚未审阅、已审阅页面、部分审阅或需要复核；
- `capture_status`：仅登记链接、已识别版本、已保存文件、已计算哈希或已归档；
- `claim.status`：直接支持、范围受限的直接支持、独立交叉验证、仅有报道、技术推断、未解决、存在矛盾或模拟数据。

这几个字段回答的是不同问题，不能相互替代。官方 README 可以直接证明公开文档写了什么，却不能单独证明历史训练任务加载了对应代码；一篇报道的多个转载也不能算成多份独立证据。

所有模拟数据都标记为 `SIMULATED`。没有原始文件时，`sha256` 与 `local_path` 留空。

## 7. 每次采集的最小记录

- 获取时间（UTC）；
- canonical URL；
- 版本、commit 或 revision；
- 本地文件路径与 SHA-256（若确实取得文件）；
- 许可与再分发限制；
- 支持的 `claim_id`；
- 局限、替代解释和下一步核验动作。

**方法论的目标不是让故事更完整，而是让每一个缺口都看得见。**
