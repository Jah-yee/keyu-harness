# 文档与代码风格

## 项目调性

Keyu Harness 可以有一点幽默感，但不拿证据开玩笑。文案可以轻，事实标准不能轻。避免煽情、定罪式措辞和把推断写成剧情的表达。

推荐的表达方式：
- “当前材料支持……”
- “这仍是一个待验证的假设。”
- “公开源码提供了比较基线，但不能证明事件时间的运行状态。”
- “此处是合成场景，不是历史工件。”

避免：
- 把未经核实的身份、组织关系或内部路径写成事实；
- 用“显然”“必然”“已经证明”替代证据链；
- 让模拟日志看起来像真实内部日志；
- 用戏谑语气掩盖来源缺失或不确定性。

## 语言分工

| 内容 | 语言 | 原因 |
|---|---|---|
| 根目录 `README.md` | 中文 | 让新读者快速理解研究目标和边界 |
| 架构、方法、基线、证据模型、路线图 | 中文 | 解释研究思路与判断标准 |
| 代码 API、模块、变量、CLI、schema key | 英文 | 与 Python 和工具链保持一致 |
| Demo 场景、日志字段、示例报告 | 英文 | 便于复制、测试、对比和 issue 讨论 |
| 论文书目 | 出版物原始语言 | 保留正式书目信息 |
| 中文报道与页面标题 | 中文原题 | 避免译名覆盖原始标题 |
| 代码注释 | 中英文均可 | 以清楚、准确为先 |

## 文件与标识符

- 文件名使用小写英文和下划线或短横线。
- Python 模块与函数使用 `snake_case`；类使用 `PascalCase`。
- 机器可读字段使用稳定英文名，例如 `source_id`、`claim_id`、`artifact_id`。
- 来源编号和主张编号一旦公开使用，不应被重新分配给另一条记录。
- 路径、版本号和哈希使用代码格式。

## 文档结构

技术文档通常按“目的 → 适用范围 → 方法/字段 → 限制 → 下一步”组织。README 保持轻量；细节放在独立文档，避免让入口页成为整份研究报告。

## 引用与来源管理

优先遵循软件与研究工件领域已有的引用实践：给出创建者、原始标题、可访问标识符，并尽可能固定版本。没有指定投稿格式时，使用常见的数字编号技术引用方式和 BibTeX 元数据；投稿时遵循目标期刊或会议规范。不要把项目文档写成在宣布一套新学术标准。
