# 研究路线：从资料包到技术考古工作台

## 当前判断

下一阶段的关键不是继续扩充事件叙事，而是把已有技术主张绑定到可复核的源码快照和工件记录。先固定材料，再解释材料；先验证工具，再使用工具得出结论。

## P0 — 纠正来源账本并固定公开基线

- 已将来源角色、审阅状态、取得状态与主张状态分开记录。
- 下一步固定 LlamaGen 与 Goku 的公开 commit SHA，并生成文件树 manifest。
- 为每个分析用的源码路径记录 commit、行号、文件哈希与许可。
- 不能取得的内部代码对象保持 `NOT_OBTAINED` / `UNRESOLVED`。

## P0 — T5 身份与缓存谱系

- 先保存 XL/XXL 的配置 revision，作为配置级比较。
- 后续分别登记 tokenizer、权重 shard、文本特征缓存、缓存生成代码和消费者任务。
- 使用配置参数和张量形状做一致性检查，但不把它们当作唯一身份凭证。
- 只有权重/缓存的实际哈希与 job load path 关联后，才能提高历史身份判断的强度。

## P1 — LlamaGen 源码审计

- 从 README、language README、公开采样入口和配置引用开始。
- 建立“文本输入 → tokenizer/encoder → feature/cache → AR model → checkpoint/output”的公开调用图。
- 为每个箭头记录源码位置和未解决问题。
- 与历史时间线比较时，保留“当前公开版本”“最接近事件时间的公开版本”“事件材料所报告的内部版本”三个独立列。

## P1 — Goku 源码与依赖基线

- 固定公开仓库的实际 commit，检查 `configs/`、`goku/`、`tools/` 和 `requirements.txt`。
- 画出公开代码的配置加载、模型构建、采样/推理入口与依赖关系。
- 公开代码若不包含某类内部训练工具，应记录为“公开材料未见”，而不是推断它不存在。
- 不把 2025 年公开依赖版本回填到 2024 年运行环境。

## P1 — PyTorch 正常行为矩阵

- 以 v2.2.0、v2.3.0、v2.4.0 作为候选公开基线。
- 对 DistributedSampler、分布式通信 API、序列化/加载路径分别做版本差异与正常行为测试。
- 报告只描述观察到的差异；是否与历史运行有关，另由运行时来源链决定。

## P2 — Harness 工程化

- 为来源表、主张表和工件表建立严格 schema 与交叉引用检查。
- 添加 config diff、文件树 diff、manifest 验证和可追溯报告生成。
- 每个报告都记录输入来源、版本、哈希、规则版本和限制。
- 所有合成案例继续标记 `SIMULATED`，不进入历史证据目录。

## 何时可以宣布一条技术结论“成立”

至少要有具体差异、运行加载证据、观测变化、时间关联、可重复对照和替代解释检查。否则就写“报告称”“公开代码显示”“技术上可能”或“仍未解决”，不要用一个更漂亮的故事代替缺失的证据。
