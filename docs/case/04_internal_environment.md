目标：回答三个问题——当初内部环境是什么样的？攻击代码是怎么插进去的？这套东西是怎么运作的？

## 3. 权限模型（本案的真正漏洞清单）

1. **共享目录同组互写**——3 月 T5 特征污染的前提（F4-S01："拥有相应权限的内部人员能够直接修改其他成员的实验文件"）。
2. **训练环境内可 sudo**——安装器能替换已安装 torch 文件（F4-S01 卡片 8）。
3. **机器粘性不校验工件**——Robust Training 保留机器状态，重启任务不核对模块哈希 → 篡改跨任务存活（F4-S01a）。
4. **关键仓库无 review**——VAR 开发仓库实习生可直接 commit（F4-S01a）。
5. **日志与检查工具在训练环境自身控制下**——可删行、可替换（F4-LP）。
6. **协作系统权限过宽**——被调查者仍在排障群、仍能进会议（F4-LP）。
7. **登录他人机器无需审批留痕到项目组**——"学习一下代码"即可解释过去（F4-LP）。

每一条都是检测配方的靶点；反过来说，**当年唯一真正起作用的探测器是团队自建的确定性复现装置**——它不依赖任何上述防护，靠"实验应可复现"的物理学性质抓到了 sampler 篡改。

## 5. 运作循环（这套东西"怎么转"）

```text
        ┌────────────────────────────────────────────┐
        │  排障群/会议：团队公开新异常、排除项、下一步   │
        └──────────────┬─────────────────────────────┘
                       ▼（信息不对称：攻击者在圈内）
   版本演进：触发概率调整 / 目标更换 / 新手段加入（挤行提交）
                       ▼
   B 层入口（T5 载体 / init.py / checkpoint 加载）
                       ▼
   C 层安装（sudo 替换 + utime）→ 机器粘性下跨任务存活
                       ▼
   症状：loss 乱飞 / 每周几次→每小时中断 / 单机异常 / 偶发卡死 / 慢
                       ▼
   D 层掩盖：日志删行 + 工具替换 + 进程隐藏 + 不可复现设计
                       └────────────► 回到排障群（闭环）
```

三个设计特征使它极难排查（F4 综合，机制解读为 H）：
1. **概率化**：不是每次都攻击，"太明显"；
2. **错位归因**：日志返回正常值（clip_grad 真 norm）、报错不触发（nonan）、单机离散异常（comm 跳过）——每个症状都指向一个无辜的常规解释（学习率、数据、机器、太阳黑子、NVIDIA 底层 bug）；
3. **自适应**：随排查进度换招，团队总结的规律下次不成立（"计算机理论似乎不成立了"）。
