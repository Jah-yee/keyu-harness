## 案例档案 00：加载即服务 LaaS（S01/S10）

**概要**：干预入口置于训练必加载的 T5 模型文件中，"能读取不同目录下的攻击代码，并执行相应的攻击"，并给机器加后门；每次实验启动随加载运行 <sup>[S10]</sup>。前传为 2024-03 的 `modify_t5`：混入单位化噪声后恢复原范数——一阶统计量不变、语义几何尽毁（机理见主 README §3.5）。

**官方基线**：无。载体实现从未公开；可对照的只有 HF 侧 config（flan-t5-xl@`efd6532` d_model=2048 / flan-t5-xxl@`d2dd233` d_model=4096，[S08][S09]）。

**报道摘录**：`modify_t5` 全函数（含三个被注释的替代分支 shuffle/keep/mixup，一行生效两行陪跑）<sup>[S01]</sup>。

**对照结论**：载体实现有三种可能——权重文件本体、加载钩子、序列化机制——公开材料无法区分；T5 型号 xl/xxl 差异同悬而未决 <sup>[S01][S04]</sup>。

**缺口清单**：
- [ ] 载体实现归属（权重 / hook / serialization）
- [ ] 被加载的真实 checkpoint、tokenizer、cache 的哈希与来源链
- [ ] xl/xxl 型号差异的时点核对（2024-03 的 LlamaGen commit）
- [ ] 与命令通道（案例 05）的关系

**检测配方**：加载前逐文件哈希 vs 登记清单；safetensors 优先、拒绝不可信 pickle；缓存谱系登记（producer 代码 revision + 输入文本版本 + 消费 job ID）。

**小结**：描述级 + 前传摘录；机制可能性已收敛到三种，待原始工件裁决。

## 案例档案 01：优化器反着跑（S01）

**概要**：`maximize = group["maximize"] = True`——每步把优化器改为"最大化损失"；adamw2 变体按 rank 取模只改部分副本，梯度已同步仍发散 <sup>[S01]</sup>。

**官方基线**：`maximize` 为 adam/adamw 合法参数（v2.1.0–v2.4.0 各 18 处引用 <sup>[S11-S13]</sup>），语义为对 loss 取反。

**报道摘录**：1 行摘录 + 卡片效果描述 <sup>[S01]</sup>。

**对照结论**：改写 param_groups 键不需要改函数体——一行即可，与"修改挤在同一行"的反取证描述相容 <sup>[S10]</sup>；部分副本最大化制造 DDP 一致性破坏：聚合无异常、轨迹分叉。

**缺口清单**：
- [ ] adam/adamw/adamw2/adamw39 四个变体的完整 diff
- [ ] 触发条件（是否概率化、是否与 GPU 数量联动）
- [ ] `raw_adamw*.py` 与 `*39`/`py9_*` 命名族的环境指向（H-FN-1）

**检测配方**：优化器参数快照（每 step 对 param_groups 关键键做哈希）；loss 方向断言（同 seed 下 loss 应单调下降，反向即告警）。

**小结**：摘录在案、语义明确；缺口集中在变体家族与触发逻辑。

## 案例档案 02：日志里的范数永远正常（S01）

**概要**：`clip_coef_clamped = torch.ones_like(clip_coef).mul_(2)`——梯度放大 2 倍，函数仍返回放大前的 norm；附带关闭 Flash/高效注意力、调高 matmul 精度、关 TF32 <sup>[S01]</sup>。

**官方基线**：`clip_coef_clamped = torch.clamp(clip_coef, max=1.0)`（v2.1.0–v2.4.0 逐字一致 <sup>[S20-S22]</sup>）——只缩不放。

**报道摘录**：1 行摘录；附带改动只有文字描述 <sup>[S01]</sup>。

**对照结论**：返回值不变意味着日志与实际更新脱节；附带改动还会改变数值路径与速度——症状被摊薄成"莫名的变慢和显存变化" <sup>[S01]</sup>。

**缺口清单**：
- [ ] 附带改动（Flash/TF32/matmul 精度）的实现与作用域
- [ ] 该函数返回值在训练框架内的消费点（哪些日志/监控读它）

**检测配方**：双路范数对账——日志记录的 norm 与独立重算的 norm 比对，比值 ≠1 即告警；数值路径指纹（matmul 精度/TF32 开关快照）。

**小结**：全案中"基线对照最干净"的一案：一行摘录、一行官方、逐字可对。

## 案例档案 03：一百台机器里的一台装死（S01）

**概要**：摘录定义 `_rank_not_in_this_group`，以 2⁻¹⁸~2⁻²¹ 概率让进程跳过集合通信；种子取自纳秒时间与对象地址 <sup>[S01]</sup>。

**官方基线**：官方 `_rank_not_in_group` 存在且共 31 个调用点；`_rank_not_in_this_group` 官方**零命中** <sup>[S32]</sup>——摘录必然省略调用点改写。

**报道摘录**：3 行 wrapper <sup>[S01]</sup>。

**对照结论**：这是全案"摘录不完整性"的实测铁证：wrapper 要生效必须改写 31 处调用点，页面从未披露该范围。数字名文件族（18/19/20/21 与 1839/1939/2039、py9_18/py9_20）疑为按触发指数与运行环境的变体 <sup>[S01]</sup>（H-FN-1）。

**缺口清单**：
- [ ] 31 处调用点的改写方式（U13）
- [ ] 数字名文件的内容与差异（指数 vs 环境）
- [ ] `data_dist` 的角色

**检测配方**：跨 rank 集合通信参与度审计（每个 collective 的期望参与集 vs 实际到达集）；通信超时与 rank 退出码的关联分析。

**小结**：摘录在案但结构性不完整；变体族是文件名考古的主对象。

## 案例档案 04：每次复现都失败（S01/S10）

**概要**：`g.manual_seed(time.time_ns() % 10000000000)` 替换 `self.seed + self.epoch`——各 rank 排列互异、跨运行不可复现，"顺带重置全局 RNG 状态" <sup>[S01]</sup>。

**官方基线**：`g.manual_seed(self.seed + self.epoch)`（v2.1.0–v2.4.0 逐字一致 <sup>[S20-S22]</sup>）。

**报道摘录**：替换行 + 官方原行并列（S01 代码 2）<sup>[S01]</sup>。

**对照结论**：这是唯一被"当场抓到"的特性——探测器是团队自建的确定性复现装置（16 位小数）<sup>[S10]</sup>；随后 mtime 纳秒级差异成为时间戳篡改的第一个物证 <sup>[S10]</sup>。

**缺口清单**：
- [ ] 涉事容器内 distributed.py 的完整副本与安装路径
- [ ] 该改动是否同时存在于多台机器（机器粘性下的扩散面）

**检测配方**：跨 rank 排列一致性（同 epoch 各 rank 索引应为严格分片）；跨运行复现校验（16 位小数口径，团队当年的装置即是范本）。

**小结**：探测器与被探测物的关系，使本案成为"确定性即安全"的教科书案例。

**小结**：描述级 + 两行摘录；与案例 00 的关系是 P0 未知。

## 案例档案 06：定点拆除（S01/S10）

**概要**：kill.py `pkill torchrun; sleep 10; pkill python`，按 TRIAL_ID/NODE_ID 触发；并"把 wait.py 写入 init.py，随训练启动自动触发" <sup>[S01]</sup>。

**官方基线**：不适用——涉事文件非框架代码。

**报道摘录**：2 行摘录 + 持久化描述 <sup>[S01]</sup>。

**对照结论**：与案例 03 构成"卡死"的两种来源（通信缺席 vs 进程被杀），互相掩护；表现为"某台机器的进程无故退出，看起来像硬件或调度故障" <sup>[S01]</sup>。

**缺口清单**：
- [ ] init.py 的注入方式与位置（U11）
- [ ] TRIAL_ID/NODE_ID 的获取途径（环境变量？调度器文件？）

**检测配方**：进程退出原因审计（kill 信号来源追溯）；启动脚本完整性校验（init.py 哈希入镜；对比容器镜像清单）。

**小结**：摘录在案；持久化机制与"三无提交"的交付方式互证。

## 案例档案 07：消失的 NaN（S01）

**概要**：加载 checkpoint 时 `v.nan_to_num_(0, 0, 0)` 就地清零 NaN/Inf，"本该报错的地方不报错" <sup>[S01]</sup>。

**官方基线**：不适用——涉事文件非框架代码。正经的 NaN 处理是 loss scaling（Mixed Precision Training，主 README 文献 [16]），不是清零。

**报道摘录**：2 行摘录，语境为"加载 checkpoint 时" <sup>[S01]</sup>。

**对照结论**：代码在加载路径上执行，说明加载路径存在可执行上下文——与案例 00 的机制描述相容；是否同一实现未知。

**缺口清单**：
- [ ] 挂接点（哪个加载函数被 hook）
- [ ] 与案例 00 载体的关系（同一系统还是两代实现）

**检测配方**：加载前后张量统计对比（NaN/Inf 计数、范数分布）；checkpoint 哈希在保存侧与加载侧双登记。

**小结**：两行摘录，机制含义大于代码体量。

## 案例档案 08：时间戳会化妆（S01/S10/S28）

**概要**：安装器（a.py/e.py/r.py/re.py/re_a.py）用 sudo 替换已安装的 torch 文件，还原属主/权限/修改时间："靠 ls -l 的时间戳排查会被误导" <sup>[S01]</sup>。

**官方基线**：不适用——涉事文件为安装器脚本。

**报道摘录**：`os.utime(local, (st.st_atime, st.st_mtime))` + sudo 动作描述 <sup>[S01]</sup>。

**对照结论**：`os.utime` 改不了 ctime——文件系统唯一不配合的元数据。当年真实发现路径正是 mtime 的"末尾两位、纳秒级"差异 <sup>[S10]</sup>；存活机制 = 就地修改 + 机器粘性（中断不释放机器、不重拉镜像，页面维护者澄清 + MegaScale 机制 <sup>[S28][S27]</sup>）。

**缺口清单**：
- [ ] 五个安装器的分工与调用链
- [ ] raw_* 备份的用途（还原？对照？）
- [ ] 被替换工具（D 反取证层）的清单——完全未公开

**检测配方**：mtime/ctime 交叉（不一致即可疑）；启动时关键模块哈希 vs 镜像清单；跨 rank 模块哈希一致性（同一 job 各 rank 应读同一容器层）。

**小结**：部署链 C 层的物证核心；检测配方中 mtime/ctime 交叉是全案性价比最高的一条。

## 案例档案 09：训练的终极优化是不训练（S01/S10）

**概要**：对外展示的 VAR T2I Demo 实为开源 PixArt-α；Prompt 自动加 "City" 前缀防同题对比；推理 Pipeline 打包为二进制交付，部署同事无法检查内部实现 <sup>[S01][S10]</sup>。

**官方基线**：PixArt-α 与 VAR 均有公开仓库与论文；输出相似、共用组件均不构成身份证明。

**报道摘录**：S01 §7 完整叙述 + "City" 前缀 + 二进制交付 <sup>[S01]</sup>；LatePost 独立收录 <sup>[S10]</sup>。

**对照结论**：双源收敛，但无原始工件；"City" 前缀是干净的反取证设计（让同题对比永不成立）；"背景里的城市建筑轮廓"长期困扰测试者，复盘才得解释 <sup>[S01]</sup>。

**缺口清单**：
- [ ] 部署二进制、权重哈希、Prompt 变换代码
- [ ] Discord 测试记录与请求日志
- [ ] 真 VAR T2I 训练的 loss 记录（"远没有达到此前对外展示的效果"的量化）

**检测配方**：发布物与训练工件哈希绑定；模型身份回显（服务启动时报 checkpoint 哈希）；Prompt 处理可审计（前缀注入检测）。

**小结**：双源叙述完整、物证为零——本案"现在能说什么/不能说什么"的最佳示范：叙述可信度与工件可信度是两个量。
